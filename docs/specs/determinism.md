# Determinism specification

This file specifies the contract that makes the simulation reproducible: the command stream that is its only input, the order and tick at which commands apply, the replay format, the per-tick state hash that detects a desync, and the float strategy. The sim crate (`crates/sim`) exists and its core is implemented, and the rule families follow; the float evidence is the `supercom-detbench` crate (`crates/detbench`), whose golden-vector tests run here and are cited as `test:` evaluators. A clause whose evaluator is a test is machine-verified; a clause whose evaluator is a pinned source or a repository path is cited, not run, and is agent-checked. Statements about the original engine rest on a pinned citation; the replay format, the hash, and the command order are this project's own design and say so. Tick length and the integer tick count come from `docs/specs/sim.md` (SIM-001, SIM-002) and are not restated here.

Every golden constant behind a test evaluator was produced on x86_64-linux. No clause claims a result on aarch64: the clauses about cross-architecture behaviour are design clauses whose tests run on x86_64, and the gap is stated in `docs/adr/0006-float-strategy.md`, which the head ratifies and which a failure of the DET-024 comparison reopens.

## Types

A ⟨Command⟩ is a record of a tick stamp (a 64-bit unsigned integer), a source slot (an 8-bit unsigned integer naming the issuing player), a sequence number (a 32-bit unsigned integer counting that source's commands across the match), and a payload (bytes the ordering never inspects). A ⟨Schedule⟩ maps each tick to the ⟨Command⟩ values applied at its start. A ⟨Digest⟩ is a 32-byte SHA-256 output. The ⟨State⟩ is the sim's full state at the end of a tick.

## Forbidden states

The sim MUST NEVER reach these states; each names the clauses that close it. A command applied twice, at a tick other than its stamp, or in an order that depends on its arrival (DET-002, DET-003). A tick begun while a source's commands for it are still open (DET-004). A replay that holds an input the sim reads and the file does not store (DET-007). Two runs of one command log that disagree without anyone noticing, or a report that names a tick earlier than the divergence or later than the first compared tick whose digests differ (DET-010, DET-011, DET-012). A NaN reaching a serialized state with a payload or sign that depends on the platform (DET-016, DET-022). A platform transcendental function in sim code (DET-014). A claim of cross-architecture equality that no replay comparison backs (DET-024).

## Command stream

**DET-001** `design` `source:docs/adr/0003-render-and-sim-stack.md`
The ⟨State⟩ at the end of tick t MUST be a pure function of the initial state and the ⟨Command⟩ values stamped for ticks 0 through t, applied in schedule order (DET-002); the sim MUST NOT read the wall clock, OS randomness, the filesystem, the network, the arrival order of commands, or the iteration order of an unordered collection, and every pseudo-random generator it holds MUST be seeded from the initial state alone. This is the command-stream interface that ADR-0003 gives the sim crate, stated as a contract; it is agent-checked until the sim crate and a replay-divergence test exist.

**DET-002** `design` `test:sim_schedule_ignores_arrival_order`
A ⟨Schedule⟩ built from a set of ⟨Command⟩ values MUST group them by stamped tick and MUST order the commands of one tick by ascending source slot, then ascending sequence number, and the schedule MUST be identical for every arrival order of the same set. The test builds the schedule from all 720 arrival orders of six commands from four sources over three ticks, and compares each with the one expected schedule.

**DET-003** `design` `test:sim_schedule_applies_at_stamped_tick`
A ⟨Command⟩ stamped for tick t MUST be applied exactly once, at the start of tick t, before any other update of that tick (building on DET-002 and the integer tick count of SIM-002); a command stamped for a tick that has already started MUST be refused as late and never applied at a later tick; two commands sharing a source slot and sequence number MUST be refused as duplicates; and which refusal is reported MUST NOT depend on arrival order. The test checks placement and count, the on-time and late boundary, the duplicate refusal across all 5,040 arrival orders of one bad set, and, for a set that is both late and duplicate, that the same refusal is reported over every arrival order; that a command's effect is in place before any other phase of its tick runs, by the first phase of a traced step being the command phase and the count of applied commands equalling the number of on-time commands.

**DET-004** `design` `source:docs/specs/sim.md#SIM-002`
The sim MUST NOT begin tick t until the set of ⟨Command⟩ values stamped for t is closed for every source slot, an empty set being a valid close, and MUST NOT measure or wait on wall-clock time: simulated time is the integer tick count of SIM-002, and the pace of ticks is the application layer's concern (SIM-005). A wire protocol that closes the sets is out of scope here; this clause fixes only what the sim requires of it.

## Replay

**DET-005** `reference` `source:https://github.com/FAForever/faf-scfa-replay-parser/blob/9d0cb7cb4bb0cf6d8be44e5c1ea4bc357aa9a0c5/replay.ksy#L8-L12`
The original's replays MUST be taken as a header followed by an operation stream, as the FAF replay parser's schema declares in its top-level sequence, the stream being operations repeated to the end of the data (lines 254-258); the same schema's operation types include advance, whose body is a 32-bit tick count (lines 174-177), set-command-source (179-182), verify-checksum, whose body is 20 bytes the schema does not decompose (189-192), and issue-command (204-234), and its operation enumeration runs from advance to lua-sim-callback (269-292). The schema is community reverse engineering, and it says nothing about how the original computes or checks that checksum.

**DET-006** `reference` `source:https://github.com/FAForever/faf-scfa-replay-parser/blob/9d0cb7cb4bb0cf6d8be44e5c1ea4bc357aa9a0c5/replay.ksy#L113-L151`
The original's replay header MUST be taken to hold the replay name and version, the map file, the mod list, the scenario, the number of command sources with their timeout allowances, a cheats flag, one player-data record per army, and a 32-bit random seed, as the FAF replay parser's schema declares for its header; that schema is the only source for these fields, and the project's header (DET-007) is its own design.

**DET-007** `design` `test:sim_replay_round_trip`
A replay MUST hold the initial state as a header (a format version, the engine version, the map, the mods or plugins, and the installed game data each identified by a SHA-256 content digest, the player slots, and the 64-bit random seed from which every generator is seeded under DET-001), then the command log, which holds every ⟨Command⟩ the match applied, then hash checkpoints (DET-008); it MUST hold nothing else that the sim reads, playback MUST need no input beyond the file and the installed game data, and a reader MUST refuse, before tick 0, a replay whose content digests do not match what is installed. The tick rate is not stored, being fixed by SIM-001. The header's fields and the empty plugin list of v0 are chosen in `docs/adr/0008-simulation-core.md`. The test writes and reads back a two-army synthetic replay, an empty one, and one that holds all six orders and two plugin entries, expects equal values, expects the content check to accept matching digests and to refuse a changed map digest or catalog digest, and expects the commands of a tick and an empty slice for a tick without commands.

**DET-008** `design` `test:sim_replay_rejects_malformed`
The command log MUST be stored in schedule order, ascending by stamped tick, then source slot, then sequence number (DET-002), each record carrying its own stamp, so that a reader reaches tick t by binary search on the stamp; hash checkpoints MUST be stored as (tick, ⟨Digest⟩) pairs ascending by tick, one for every tick at which the writer chose to record one, and a reader MUST reject a log whose records are not in schedule order or a checkpoint list that is not ascending; a record is out of order when it is not after its predecessor, a checkpoint when its tick is not greater than its predecessor's, and a refusal names the index of that record. A reader MUST also refuse a ⟨Command⟩ whose `(source, seq)` pair an earlier record already holds, which no single tick's batch can show (DET-003), and a record whose army is not the army of the player slot its source indexes, so that a command's army is bound to its source. Every length and count the reader meets MUST be checked against the bytes that remain before anything is allocated for it. The format is chosen in `docs/adr/0008-simulation-core.md`. The test cuts a valid file at every byte, and corrupts it once per refusal: magic, version, record order, a repeated pair, a foreign army, checkpoint order, an unknown order tag, an unknown queue mode, a non-UTF-8 string, and lengths and counts of `u32::MAX` in inputs too short to hold them.

## State hashing and desync detection

**DET-009** `design` `test:sim_serialization_is_canonical`
The canonical serialization S of a ⟨State⟩ MUST use a fixed field order, little-endian integers, `f64` values as the bit patterns that DET-022 gives them, and every collection in ascending identifier order, never in the iteration order of a hash table, so that two builds of the sim on any supported platform give equal bytes for equal states; the field order is documented on the serializing function and chosen in `docs/adr/0008-simulation-core.md`. The test builds equal states by inserting the same entities and armies in different orders and expects equal bytes, puts NaNs of both signs and several payloads in a position and expects the canonical pattern, and compares a minimal state with a byte vector it states from the documented field order. DET-010 fixes what is done with S.

**DET-010** `design` `test:sim_tick_hash_chain_bits`
After every tick t the sim MUST compute the ⟨Digest⟩ H(t) = SHA-256(H(t-1) || LE64(t) || LE64(length of S) || S), where S is the canonical serialization (DET-009) of the ⟨State⟩ at the end of tick t, H(-1) is thirty-two zero bytes, and LE64 is a 64-bit little-endian integer. The test computes the chain over a 16-tick synthetic state sequence, compares the first and last digests with committed values, and rebuilds two links by hand from the stated layout with an independent code path.

**DET-011** `design` `test:sim_tick_hash_localizes_divergence`
Two runs whose states first differ at tick d MUST have equal digests at every tick before d and unequal digests at every tick from d on, so that the first unequal digest names the first divergent tick; a sequence that is a proper prefix of another MUST be reported as diverging at its own length. The test flips one byte of the state at each tick of a 40-tick sequence in turn and checks the reported tick, the equal prefix, and the unequal suffix.

**DET-012** `design` `source:docs/adr/0003-render-and-sim-stack.md`
A peer or a replay reader that finds unequal digests at tick t MUST report a desync as an interval, from the last compared tick whose digests agreed (exclusive) to the first compared tick whose digests differ (inclusive), since checkpoints exist only at the ticks a writer chose (DET-008) and the divergence lies in that interval (DET-011), and MUST NOT go on treating the run as in sync; what a lockstep session then does with the diverged peer is a policy this clause leaves open.

**DET-013** `derived` `test:sim_scheduled_run_ignores_arrival_order`
Following from DET-002, DET-003, and DET-010, two runs of one initial state over one set of ⟨Command⟩ values MUST have equal digests at every tick whatever order the commands arrived in. The test runs the sim state, two armies and four entities, over all 720 arrival orders of six commands and expects one digest sequence; as a control it applies the same commands in arrival order within each tick and expects at least two distinct final digests, so that the digest is shown to be order sensitive.

**DET-025** `design` `test:sim_rng_is_seeded_from_initial_state`
Every pseudo-random generator the sim holds MUST be written in the sim crate and seeded from the initial state alone (DET-001, DET-007), so that equal seeds give equal output sequences, unequal seeds give unequal ones, and two states with one seed give one digest sequence over one schedule; the generator is chosen in `docs/adr/0008-simulation-core.md`. The test compares the first 64 outputs of equal and unequal seeds and the digests of two seeded states over 8 ticks.

**DET-026** `design` `test:sim_replay_fixture_is_byte_exact`
The replay file MUST be laid out as follows, every integer little-endian: the eight bytes `SCREPLAY`; the format version, a `u32`, 1 in this version; the header, being the engine version and the map, each a string, the map content digest and the installed-data catalog digest, each 32 bytes, a `u32` plugin count then per plugin a string name and a 32-byte digest, a `u32` player count then per player an army `u8` and a string name, and the seed, a `u64`; a `u32` command count then each ⟨Command⟩ as follows (tick `u64`, source `u8`, sequence number `u32`, army `u8`, unit count `u32` then the ids as `u32`, queue mode `u8`, order tag `u8` then its fields, `f64` values as the bit patterns of DET-022, strings as below); and a `u32` checkpoint count then per checkpoint a tick `u64` and a 32-byte digest. The order tags are 0 Move (a position, three `f64`), 1 Stop (no fields), 2 Attack (a target id, `u32`), 3 BuildMobile (a blueprint string then a position), 4 BuildFactory (a blueprint string), and 5 Guard (a target id, `u32`); the queue-mode values are 0 Replace and 1 Append. A string is a `u32` byte length then that many UTF-8 bytes. The player at index i is the slot of source i. Version 1 writers write no plugins, because the first release runs none, and the reader parses any number but the content check refuses a non-empty list. The reader is strict, accepting exactly the bytes the writer can produce: it MUST refuse bytes after the last checkpoint (`TrailingBytes`) and any `f64` field whose bits are a NaN other than the canonical pattern (`NonCanonicalFloat`). This is the project's own format, not the original's (DET-006), chosen in `docs/adr/0008-simulation-core.md`. The committed synthetic replay `crates/sim/fixtures/synthetic.replay` is its golden vector, produced by a reference encoder in the test that shares no code with the writer; the test expects the encoder to reproduce the file, the sim's writer to reproduce it byte for byte, and the sim's reader to parse it to the value the encoder was given.

**DET-027** `design` `test:conformance_sim_replay_digests_equal`
One command log on an installed map, replayed twice in one process from the committed file `crates/replay-harness/fixtures/skirmish_scmp_012.replay`, MUST give equal ⟨Digest⟩ values at every tick (DET-010), and those values MUST equal the file's checkpoints, which an earlier process wrote. The log is a fixture generated by committed code, under 4 KiB, holding identifiers and numbers only; the world is checked against the header before tick 0 (DET-007, DET-030). The digest program, run as two processes, MUST print equal bytes (`conformance_sim_replay_two_processes_agree`). The record is `docs/adr/0015-replay-harness.md`.

**DET-028** `design` `test:conformance_sim_replay_diverges_at_altered_tick`
Moving one command's stamp of the committed log by one tick, with the log re-sorted, MUST change the digests from the earlier of the two ticks on and not before, and the first divergence (DET-011) MUST name that tick; a comparison that cannot fail proves nothing. The record is `docs/adr/0015-replay-harness.md`.

**DET-029** `design` `test:conformance_sim_replay_covers_manifest`
The committed log MUST exercise every rule family that the digest comparison is meant to cover: at its end the counters for moves completed, builds completed, projectile impacts, and deaths MUST each be above 0, the stall ticks at least 1, the defeats exactly 1, the victories exactly 1, and the kills exactly 1. The record is `docs/adr/0015-replay-harness.md`.

**DET-030** `design` `test:sim_replay_start_refuses_a_wrong_header`
The replay-start constructor, `World::replay_start`, MUST refuse before any state exists a header whose map or catalog digest differs in one byte from the world's (DET-007), a header with a non-empty plugin list, a header whose player string is not exactly one faction's name (`UEF`, `Aeon`, `Cybran`, or `Seraphim`, case-sensitive), and a header whose player slots are not the armies 1, 2, 3, and so on in order (the player at index i holds slot i + 1); it MUST check the content first, so a header wrong in both ways reports the digest. Otherwise it MUST start the skirmish (SIM-051) of the factions the strings name, in player order, from the header's seed. Version 1 of the format gives the player string this meaning so that the file and the installed data are enough to start a match (DET-007) and no field is added; the record is `docs/adr/0015-replay-harness.md`. The test starts a synthetic world from a matching header, then flips each of the first and last byte of each digest, changes the string of one player to five wrong values, swaps the slots, skips a slot, and corrupts both a digest and a string at once; it then starts a synthetic world with the four commanders from a header naming Seraphim, Cybran, Aeon, and UEF in slots 1 to 4 and checks that the armies 1 to 4 hold `xsl0001`, `url0001`, `ual0001`, and `uel0001`, and checks that `run_replay` refuses a header whose catalog digest differs in one byte.

## Float strategy

**DET-014** `reference` `source:https://github.com/rust-lang/rust/blob/b940084d7eb6a299eb4bfeb8e34901bc051e7ac4/library/std/src/num/f64.rs#L680-L686`
Sim code MUST NOT call the standard library's `f64` transcendental functions, which include `sin`, `cos`, `tan`, `atan2`, `exp`, `ln`, `powf`, `powi`, `cbrt`, and `hypot`: the standard library documents the precision of `sin` as non-deterministic, varying "by platform, Rust version, and can even differ within the same execution", and gives the same text to every function of that group (lines 308 through 1249 of the same file at rustc 1.99.0).

**DET-015** `reference` `source:https://github.com/rust-lang/rust/blob/b940084d7eb6a299eb4bfeb8e34901bc051e7ac4/library/core/src/primitive_docs.rs#L1223-L1236`
Sim code MAY use binary64 addition, subtraction, multiplication, and division, which the standard library documents as rounded to nearest with ties to even under IEEE 754 (the `f64` page defers to the `f32` page, lines 1387-1391), and MAY use `sqrt` and `mul_add`, which the `f64` documentation describes as the IEEE 754 results and "guaranteed not to change" (library/std/src/num/f64.rs lines 192-196 and 364-368); the documented guarantees cover the value of a result that is not a NaN.

**DET-016** `reference` `source:https://github.com/rust-lang/rust/blob/b940084d7eb6a299eb4bfeb8e34901bc051e7ac4/library/core/src/primitive_docs.rs#L1262-L1292`
Sim code MUST treat the sign, quiet bit, and payload of any NaN, whatever its origin, as unspecified, and MUST NOT read a NaN's bits (`to_bits`, `total_cmp`, `is_sign_positive`, `is_sign_negative`, `copysign`) before DET-022 has canonicalized it: the standard library documents the sign as non-deterministic, the quiet bit and payload as chosen non-deterministically from a set of preferred, propagated, and target-specific patterns, and says that running one operation twice on the same inputs can give different bit patterns.

**DET-017** `reference` `source:https://github.com/dimforge/rapier/blob/3406750a38286a0d3c7d0f4be2f9d53153e81d90/crates/rapier3d/Cargo.toml#L76`
The float strategy MAY rely on a pure-Rust `libm` in place of the platform's as a precedent already shipped in a physics engine: the rapier3d manifest defines its `enhanced-determinism` feature as enabling `simba/libm_force` and `parry3d/enhanced-determinism`. The manifest states the feature's components and not its guarantees, so this clause is a precedent and not evidence of equality across platforms.

**DET-018** `design` `test:detbench_basic_ops_bits`
On x86_64, binary64 addition, subtraction, multiplication, division, and the square root of an absolute value MUST give the committed bit patterns over six fixed operand pairs that include a subnormal, an overflow to infinity, and an underflow to zero; `libm::sqrt` and `f64::sqrt` MUST agree bit for bit with each other and with the committed square roots of twelve inputs; and a separate multiplication and addition MUST NOT be fused, while `mul_add` is fused and exact, shown on an operand set whose fused and unfused results differ.

**DET-019** `design` `test:detbench_libm_sin_bits`
Every sine in sim code MUST be computed with the `libm` crate, and on x86_64 `libm::sin` MUST give the committed bit patterns over fourteen fixed inputs, which include an argument of 1e10 that takes the long argument-reduction path and one of 1e5 that takes the medium one, both with the crate's `arch` feature off (`cargo nextest run -p supercom-detbench`) and on (`cargo nextest run --workspace`, where Cargo enables it through the plugin host's dependencies); the feature only swaps assembly in for operations that are exact either way.

**DET-020** `design` `test:detbench_libm_exp_bits`
Every exponential in sim code MUST be computed with the `libm` crate, and on x86_64 `libm::exp` MUST give the committed bit patterns over fourteen fixed inputs, which include arguments whose results are subnormal (-740) and nearly overflow (709.5), in both feature configurations of DET-019.

**DET-021** `design` `test:detbench_fixed_mac_bits`
A quantity that needs exact reproducibility without floating point MAY be held in the 64-bit fixed-point format with 32 fractional bits; its multiplication MUST round toward negative infinity, and a multiply-accumulate sequence over eight fixed operand pairs, which includes a negative product smaller than one raw unit, MUST give the committed raw accumulator after every step and MUST equal the same sequence in 128-bit integer arithmetic.

**DET-022** `design` `test:sim_serialization_is_canonical`
Every `f64` that enters a serialized ⟨State⟩, a ⟨Digest⟩, or a replay MUST be passed through a canonicalization that maps every NaN, of either sign and any payload, to the bit pattern 0x7ff8000000000000 and leaves every other value's bits unchanged; this is also the pattern the plugin host's test `sandbox_nan_bits_are_canonical` observes for a NaN that a guest's arithmetic produces, while a NaN a guest builds without arithmetic keeps its bits, which are the same on every host (read from the compiler's canonicalization pass, not shown by a test: the plugin test divides zero by zero), and this clause canonicalizes it too, so a NaN from a plugin and a NaN from the sim hash alike, and a sim that never produces a NaN, by construction, satisfies the clause trivially.

**DET-023** `reference` `source:https://docs.rs/wasmtime/49.0.2/wasmtime/struct.Config.html#method.max_wasm_stack`
A limit on guest recursion set as a byte budget of native stack MUST NOT be assumed to trap at the same call depth on every host: the wasmtime documentation says of `max_wasm_stack` that the number "is not super-precise" and that wasm will take at most "pretty close to this much" stack space, and the plugin host sets exactly such a budget (`MAX_WASM_STACK_BYTES` in `crates/plugin`).

**DET-024** `design` `source:docs/adr/0006-float-strategy.md`
The project MUST NOT claim bit-identical simulation across x86_64 and aarch64 until one command log, replayed on both, gives equal ⟨Digest⟩ values at every tick (DET-010). The comparison is the digest program of `crates/replay-harness` run on both hosts by `tools/replay_compare.sh`, which compares the two outputs byte for byte, and it MUST include two cases. The payload-NaN case places in an entity's position a NaN the host's own arithmetic produces from zero over zero and a NaN a plugin's result produces through the host, steps the sim ten ticks, and prints each digest; the digests agree only because of DET-022, and the raw bits of both NaNs are printed outside the compared output. The recursion case probes by bisection, through the host with a fresh instance per probe, the largest depth to which a component whose step recurses to the depth its tick argument names still returns; that depth is printed outside the compared output and recorded in ADR-0006 rather than compared, because DET-023 says the budget differs between hosts, and the compared output keeps only the kind of trap an unbounded recursion raises, stack exhaustion rather than fuel or a crash. This version runs no plugin inside the tick loop, so the harness drives the host from outside the sim (`docs/adr/0015-replay-harness.md`); a plugin entering the tick loop needs a deterministic depth bound below the smallest depth measured over every host and build profile the tick loop ships on, the signpost of this case. The evidence is the recorded comparison in `docs/adr/0006-float-strategy.md` (its section on the replay comparison): it passed for the committed log on two Linux hosts at one commit, so DET-018 through DET-022 hold on both; the comparison in CI and on aarch64-darwin remain open (AGENTS.md U1).
